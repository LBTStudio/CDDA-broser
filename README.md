# Cataclysm: DDA 0.I — ブラウザ版ビルドキット

👉 はじめての方は `README-はじめにお読みください.md` を開いてください。
GitHub Actions が最新安定版 0.I "Ito" を自動でブラウザ版に組み立て、GitHub Pages に公開します。
Chromebook は Linux 不要・Chrome で URL を開くだけです。

## 特徴
- 最新安定版 0.I "Ito" (2026-06-06) を WebAssembly でブラウザ実行
- プレイヤー名ごとにセーブデータを完全分離（初回起動時に名前入力）
- セーブのエクスポート（zip バックアップ）機能つき
- リポジトリは約 1MB で GitHub の 25MB 制限に引っかからない
- 重い成果物（wasm 約45MB＋データ約68MB）は CI が毎回生成して Pages へ直接公開

## RAM 4GB Chromebook 向けの安定化（このリポジトリ独自）

### 現在の評価と設計基準（2026-09-08）

**4GB Chromebookで本家の推奨環境と同等に動く、という実測上の保証はまだありません。**
RAM容量だけではCPU性能・ブラウザの負荷を決められません。既存のF-18/F-20の
「72%」「31%高速化」「低速機で合格」は合成ベンチの値であり、実ゲームや
4GB実機で測った結果ではありません。これらを達成判定の根拠から外します。

**禁止する最適化:** 敵/NPCの数やAI更新、危険検知、ゲーム内ターン、ゲームルールを
削減して処理を軽くすること。タイルやMODを削ることも目標達成の代用にしません。

今回の実装（PR #10）:
- 危険検知の16ターン間引きを撤回し、本家の3か所の呼び出しを復元しました。
  `mon_info_update()` は表示だけでなく行動中断・安全モードにも作用します。
  **この撤回だけなら処理量は増えますが、ゲーム体験の互換性を優先します。**
- 表示しないターンでは進捗文字列・死体の走査・中断キー説明を作りません。
  ゲームから抽出した待機表示コードの回帰テストで、読書1800ターンの
  文字列生成を **1800回→31回** に削減。表示時刻・表示内容は一致しました。
  **これは文字列生成回数の削減であり、ゲーム全体が約58倍速くなる意味ではありません。**
- 敵/NPCのAI処理境界と睡眠中にも時間予算付きyieldを設けました。
  AIの順番・処理内容は変えず、ブラウザの無応答を減らすための修正です。
  1回のAI処理自体が長い場合もあり、16ms以内の応答を保証するものではありません。
- wasmの未読Responseクローンを廃止し、初期化後に保持していた参照を解放します。
  ダウンロード全チャンクをJavaScriptの配列で保持する処理も廃止しました。
  実機でのピークRAM削減量は未測定です。

検証:
- `bench/runtime_efficiency_test.py`: 実ソースから取り出した表示コードの224条件を
  上流と比較。睡眠、読書、粉砕、製作、運転、応急処置、非表示メニュー、
  中断設定、活動終了・再開を含みます。AIのコードはyield以外で一致することを確認。
- `bench/asset_loader_test.js`: 実HTMLローダーのキャッシュ、304、オフライン、
  容量不足、MIME不一致、streaming失敗、破損データ、参照解放を検証。
- 実際の `do_turn.cpp` / `player_activity.cpp` のEmscripten構文検証は合格。
- **フルビルド後の実プレイ、4GB実機でのピークメモリと長時間安定性、
  推奨環境のネイティブ版との比較は未完了です。単体テスト合格で代用しません。**

今後の達成判定は、同じ0.I・セーブ・設定・MOD・タイル・解像度を使い、
初回/再起動ロード、死体の連続粉砕、30分の読書、8時間の睡眠、
都市部で多数の敵/NPCがいる場所の連続移動、長時間探索後のセーブ/再ロードを比較します。
計測対象は完了までの実時間、入力から結果描画までのp50/p95/最大値、
描画停止時間、ブラウザ全体の使用メモリ、OOM/タブ破棄/セーブ復元失敗の有無です。
AI・視界・マップ処理・保存同期の時間を分け、支配的な処理から次の改善を行います。
単にyieldを増やしても総処理時間は短くならないため、応答性と処理速度は別々に評価します。

以下は既存の機能・修正履歴です。古い合成ベンチ由来の性能説明より上記の評価を優先してください。

- **世界生成中のフリーズ対策**: JSON ロード・MOD 相互作用・ファイナライズ・
  オーバーマップ生成・マップ生成の各段階で 50ms ごとにブラウザへ制御を返す
  パッチを適用（`patches/` 参照。すべて Emscripten ビルド限定）
- **世界生成「後」の最終処理フリーズ対策**: マップ・オーバーマップの保存、
  JSON 検証、ワールドのシリアライズなど本家が `pump_events()` を置いている
  全ループが Web でも実際にブラウザへ制御を返すよう `pump_events` 内部に
  50ms 間隔の yield を追加（「ページを離れる/待機」ダイアログの解消）
- **キャラ作成直後の "Exception thrown" 停止の修正**: セーブ永続化の
  コールバック (`setFsNeedsSync`) が非同期の初期リストアより先に定義される
  よう修正。IndexedDB が使えない環境ではセーブ保存なしで続行し警告を表示
  （起動が例外で停止しなくなった）
- **圧縮セーブ由来のクラッシュ修正**: ブラウザのファイルシステム (MEMFS) は
  「一度も書き込まれていない空ファイル」を mmap すると JavaScript の
  `TypeError (reading 'buffer')` を投げるため、作成直後の圧縮セーブ
  (`.zzip`) を開いた瞬間にゲームが停止していた。空ファイルは POSIX と同様に
  「マップ失敗」として扱い既存の復旧経路（フッター再生成）へ流すよう修正。
  あわせて Web 版ではワールド圧縮のデフォルトを OFF に変更
  （オプション自体は残っており、ワールドごとに ON にすることは可能）
- **日本語入力（IME）対応**: ブラウザの IME はフォーカスされた編集可能な
  DOM 要素にしか変換を出せないため、ゲーム内の入力欄（セーブ名・検索など）
  で日本語が打てなかった。不可視の入力プロキシを設け、ゲームが文字入力を
  受け付けている間だけフォーカスし、変換中のプレビューと確定文字列を
  SDL のテキストイベントとしてゲームに再注入する方式で対応
  （変換中の Enter / 矢印 / Esc は IME 専用として扱いゲームに漏らさない）。
  さらに、プロキシのフォーカスは「実際に文字入力欄が開いている間」
  （文字入力ポップアップ・テキストエディタ・キー割り当て検索）だけに限定。
  以前は通常のマップ移動中もプロキシがフォーカスされ続けたため、日本語 IME
  が ON のままだと移動キーがかな変換に吸われて操作不能になっていた
- **SIGILL クラッシュ対策**: ワールド作成直後・キャラ作成直後のロード中に
  まれに出ていた SIGILL 型トラップは、Asyncify 退避バッファ枯渇と wasm
  スタック枯渇の 2 系統。バッファを 16MB・スタックを 4MB に拡大して解消
  （どちらも一度きりの確保で、プレイ中のメモリ消費は増えない）
- **動作の高速化**: リンク最適化を `-O0` から本家標準の `-Os` に変更。
  Asyncify 計装が未最適化のまま残ることが操作のもたつきの主因だったため、
  プレイ中の体感速度が改善し、wasm のダウンロードサイズも約半分になる
- **MODの後入れ対応**: 設定メニューの「Install Mod (zip)」から MOD の zip を
  選ぶだけで導入可能（ビルド不要・リロード後に反映）。「Manage Mods」で
  一覧・削除。導入先はプレイヤーごとのセーブ領域内 `mods/` で、
  セーブと同様に IndexedDB に永続化される
- **Stats Through Kills 同梱**: キル経験値でステータスを上げられる公式 MOD
  （0.I 本体からファイルだけ削除されたがエンジン側の対応は健在）を同梱
- **JSON 解析キャッシュの永続化（2 回目以降の「コア読み込み・最終処理」を短縮）**:
  ゲームは約 60MB のコア JSON を解析した結果（FlexBuffer バイナリ）をディスクに
  キャッシュする仕組みを本来持っているが、Web 版ではその置き場所が
  リロードごとに消える一時ファイルシステム（MEMFS）にあり毎回全解析していた。
  キャッシュ置き場を IndexedDB に永続化されるセーブ領域へ移し、データ
  パッケージの ETag をキーに世代管理（ゲーム更新で自動的に作り直し、旧世代は
  自動削除）。2 回目以降のキャラ作成前ロードが大幅に短縮される
- **マップ移動の軽量化**: (1) コンパイル最適化を本家 Web 標準の `-Os`
  （サイズ優先）から `-O3`（速度優先）へ変更。移動のたびに走る mapgen /
  イベント / AI 処理のホットループが速くなる（リンク段の `-Os` は維持しつつ、
  永続キャッシュのおかげでダウンロード増も一度きり）。(2) 毎ターン走っていた
  Asyncify の全スタック退避・復元（描画後の `emscripten_sleep(1)` と
  `pump_events` の 50ms 間隔 yield）をそれぞれ約 30fps 相当・250ms 間隔に
  間引き、ターンあたりの固定オーバーヘッドを削減
- **連続ターン処理**: 上記のとおり、危険検知の間引きは撤回済みです。
  ゲーム進行を省略せず、未表示の進捗生成とブラウザ側の不要な保持を削減します。
  過去のF-18/F-20にある合成ベンチの速度比は実プレイの速度を表しません。
- **アセットの永続キャッシュ（2 回目以降の起動を数秒に）**: GitHub Pages は
  `max-age=600`（10 分）でしか HTTP キャッシュを許さず、約 120MB の
  wasm+データを訪問のたびに再ダウンロードしていた。Cache Storage API に
  期限なしで保存し、`navigator.storage.persist()` でディスク圧迫時の退避から
  保護（セーブデータの IndexedDB も同時に保護される）。ETag の条件付き GET で
  新デプロイは自動検知し、オフラインでもキャッシュから起動できる。
  wasm は `instantiateStreaming` で読み込みとコンパイルを同時進行。
  Cache Storage が使えない環境では従来のローダーに自動フォールバック
- **メモリ方針**: wasm線形メモリは起動時256MB・上限2GB（成長方式）。
  これはページ全体のRAM上限ではありません。別途JSヒープ、MEMFS/IDBFS、
  コンパイル済みコード、画像/GPU、ブラウザ本体、ChromeOSのメモリが必要です。
  上限を2GBにしただけでは4GB端末での安定性を保証できません。
- **Asyncify スタック 16MB**: 深い呼び出し中の yield でも状態が壊れないように
- **セーブの確実な永続化**: 従来は IDBFS のマウント先が固定パス
  (`/home/web_user`) でプロファイル別のセーブが揮発性メモリに書かれ、
  リロードで消えていた。マウント先を各プロファイルの HOME に追従させて修正
- **セーブ書き込みの間引き**: 世界生成中の大量ファイル書き込みを 250ms 単位で
  まとめて IndexedDB へ永続化（1 ファイルごとの同期をやめて負荷を削減）。
  タブ非表示・ページ離脱時に同期を要求しますが、非同期保存の完了前に
  ChromeOSがタブを破棄すると直前の変更を失う可能性があります。バックアップが必要です。
- **エラーの見える化**: 黒画面のまま止まらず、日本語の対処ヒントつき
  エラー画面を表示（メモリ不足時は「他のタブを閉じて再読み込み」を案内）

## ビルドの動かし方
Actions タブ →「Build CDDA 0.I WebAssembly」→ Run workflow。

### PRの導入手順・必要作業

1. 更新前にゲーム内でセーブし、設定の **Export Saves** でバックアップします。
2. 対象PRを **mainにマージ**します。PR #10は処理改善、PR #11は追加検証・手順です。
3. Actionsから上記ワークフローを実行します。**ブランチmain、shards=8、
   link_opt=O2、deploy_pages=true** が公開用の設定です。
4. ビルド・検証・Pages公開がすべて成功するまで待ちます。**マージだけでは
   公開中のゲームは更新されません。C++変更を含むため再コンパイル・再リンクが必要です。**
   所要時間はキャッシュやランナーに依存し、初回は数時間かかる場合があります。
5. 開いていたゲームを保存してページを再読み込みします。同じプレイヤー名を選びます。
   セーブ形式は変更していません。**サイトデータ削除・セーブ初期化は不要です。**
6. 粉砕・読書・睡眠・都市部の移動と、敵接近時の警告/行動中断を確認します。

公開前に試す場合は **deploy_pages=false** でビルドし、成果物を検証します。
この設定では現在の公開サイトは更新されません。公開する際はtrueで再実行してください。
`ci/apply-patches.sh` がビルド前に回帰テストを実行し、失敗時は処理を止めます。
GitHub Actions上では追加インストール作業は不要です。手動でパッチを検証する場合は
Python 3、C++17対応g++、Node.js 22を用意し、未改変0.IをHEADに持つソースツリーを使用してください。


入力欄は 2 つあります。

- `deploy_pages`: チェックを外すと Pages を更新せずビルド成果物（artifact）
  だけ作れるので、公開前の動作確認に使えます。
- `shards`: コンパイルの分割数（既定 8）。大きくすると並列数が増えて速く
  なりますが、`.o` ファイルの受け渡し量も増えるため、増やしすぎると
  かえって遅くなります。迷ったら既定のままで問題ありません。

### ビルド時間について（4 時間 → 分割並列化）
以前は 1 つのジョブで全部を順番に処理していたため約 4 時間かかっていました。
現在は処理を 6 つのジョブに分け、独立している部分を同時に走らせています。

```
    plan ──┬──> compile（8並列）──> link ──┐
           │                                ├──> bundle ──> deploy
           └──> data ───────────────────────┘
```

- **コンパイル（440 ファイル）を 8 並列に分割**: 1 ジョブあたり 55 ファイル。
  ファイルの割り当ては「先頭から等分」ではなく飛び飛び（8 個ごと）にして
  います。ファイル名順に並べると重いファイル（mapgen 系・monster 系）が
  固まってしまい、等分すると 1 つのジョブだけが極端に遅くなるためです
- **データ同梱を別ジョブで同時実行**: 約 68MB のデータパッケージ作成は
  wasm の完成を待つ必要がないので、コンパイル・リンクと並行して進めます
- **ccache でコンパイル結果を再利用**: 2 回目以降のビルドで、変更のない
  ファイルの再コンパイルを省略します（実測で該当ファイルは 7 秒 → 0 秒）
- **リンクの工程も速くしました（従来「不可能」と書いていたのを訂正）**:
  実測すると、ビルド 4 時間 23 分のうち
  **wasm-opt 1 個で 4 時間 02 分（93%）** を占めていました。
  しかも 4 コアのうち **1.05 コアしか使っていない** ため、
  マシンを強くしても速くなりません。
  遅い原因は Asyncify ではなく **インライン展開（71%）** だったので、
  最適化レベルを下げれば実際に縮みます（実測 `-O2` で **-20%**、
  `-O1` で **-78%**、サイズ増はどちらも約 +2.6%）。
  Actions の実行時に **`リンク最適化レベル`** を選べます。
  - `O2`（既定・配信用）… リンク約 3 時間 14 分
  - `O1`（検証用）… リンク **約 53 分**
- **リンク結果のキャッシュ（いちばん効きます）**: wasm-opt は
  入力（440 個の `.o` ＋リンク引数）が同じなら出力も同じなので、
  前回と入力が一致したら **4 時間を丸ごと省略**します。
  データ・MOD・HTML・設定だけを直した場合はこれに該当し、
  **約 15 分**で終わります。
  - 判定は `.o` の**内容**ハッシュで行うので、
    ファイルの日時が変わっただけでは無駄に作り直しません
  - 逆に部分一致では絶対に当てません（「直したのに古いものが
    公開される」事故を防ぐため、完全一致のみ許可）
- **リンク工程での無駄な作り直しを止めました**: 分割ビルドの初回実行
  （run 33888888789）では、リンク担当のジョブが **440 個中 406 個を
  再コンパイル**しており、約 19 分を捨てていました。
  原因はコンパイラが残す依存メモ（`.d`）に **絶対パス**が書かれていることです。
  GitHub Actions はジョブごとに **毎回違う UUID のフォルダ**へ
  emsdk を展開するため（9 ジョブすべて別でした）、リンク側から見ると
  その参照先が存在せず、`make` が「古い」と誤判定していました。
  日時を揃える（`touch`）だけでは **原理的に防げません**。
  リンク段では `.d` を削除するようにして、作り直しをゼロにしました。

### 進捗バー
時間のかかる工程（各コンパイル・データ同梱・リンク）にはログ上で進む
進捗バーが出ます。GitHub Actions のログは追記専用で行の上書きができないため、
一定間隔で新しい行を出す形式です。

```
[PROGRESS] compile shard-2 [############------------------]  40% ( 22/ 55) 経過 3m12s 残り推定 4m48s
```

各ジョブは Actions の Summary 欄にも 1 行ずつ結果を書き出すので、
どのジョブが一番遅かったかをログを開かずに確認できます。

## 技術詳細
docs/ARCHITECTURE.md を参照。ローカルビルド: `bash scripts/build-local.sh`（8GB RAM 以上の Linux/mac）。
実測データと技術的な事実確認の記録は `docs/measurements/FACTS.md`（F-01〜F-29）にまとめています。

- **F-29**: 「粉砕・睡眠・読書などで現実時間が膨大にかかる」問題の調査中に、
  **これまで根拠にしてきた「1 ターンのコスト」が 2 つとも合成ベンチの値**
  だったことが判明しました（F-18 の 0.8600ms は `burn(60000)` という
  空ループの手決め定数、F-01 の 0.1030ms は仮想呼び出しを模した合成コード。
  **両者は 8.3 倍食い違っています**）。
  「本家 CDDA と同等の処理時間に収める」には自分の実値が必要なので、
  アクティビティ終了時に `[perf] smashing: 30 turns in 60 ms (2.000 ms/turn)`
  を出す**実測基盤**を入れました。次の最適化はこの数値を見てから決めます。
  併せて、**粉砕に進捗表示が無かった**（`get_progress_message` が未実装で
  `Smashing…` しか出ず、残り死体数も進捗率も分からない）のを修正し、
  `3 corpses left (45%)` を出すようにしました。
  なお進捗更新をリアルタイム基準にする案は、**ターン基準こそゲームに
  即している**という方針、および「実処理時間が長い」本質に蓋をするだけ
  という理由で**却下**しています。

- **F-28**: 「短時間に何度も移動すると追いつかなくなる」の真因は
  **押したキーが実際に捨てられていた**ことでした。処理が遅いのではありません。
  `CheckMessages()` は 1 回で SDL キューを最後まで飲み干す（577 行のループで、
  抜ける経路は移動キーでは発火しないもの 1 個だけ）のに、受け皿は
  `last_input` という**単一変数**なので、飲んだ分は最後の 1 個以外すべて
  上書きで消えます。さらに `pump_events()`（src 内 **35 箇所**から呼ばれる）は
  飲んだ結果を**明示的に破棄**していました。
  ブラウザは wasm がメインスレッドを占有している間 keydown を溜め込み、
  yield の瞬間にまとめて配送するため、素早く押すほど消える割合が増えます。
  実測では**ターン処理中に 10 回押して処理されたのは 0 回**でした。
  FIFO キュー（上限 64）で補完し、**押した回数と処理される回数が完全一致**
  するようになりました（20 回 → 修正前 0〜1 回、修正後 20 回）。
  キューが空の通常時は全分岐を素通りするため、従来の挙動は変わりません。

- **F-27**: 配信された wasm がブラウザで起動しない事故
  （`size 7657177 > maximum function size 7654321`）の原因を特定しました。
  V8 には「1 関数あたり 7,654,321 バイト」の上限があり、
  1 つの関数が 7.6MB に膨らんで超過していました。
  動いていた過去のビルドと比較すると **上限の 97.45%（余裕 195KB）**
  という崖っぷちで、**元から壊れる寸前だった**ことが判明しました。
  原因は Binaryen の `-ocimfs`（既定 -1 = 無制限）で、
  制限を入れると最大関数が **−87%** になり動作は変わりません。
  併せて `ci/verify-wasm.sh` を追加し、
  **同種の事故は CI で止まる**ようにしました
  （em++ の終了コードは壊れていても 0 のため、生成物を直接測る必要があります）。

- **F-26**: リンク時間の 71% を占める `inlining-optimizing` パスは、
  emsdk 3.1.51 同梱の Binaryen 116 より後の上流 PR（#6966 / #6967）で
  高速化されていました。`wasm-opt` を版 132 に差し替えることで
  実測 **-37.8%**（出力サイズは +0.14%）、リンク段は
  **242 分 → 約 148 分**の見込みです。
  ただし版 132 は `-Os` / `-O3` / `-Oz` を使うと
  **ビルドは成功するのに実行時に**壊れる（`LinkError`）ため、
  最適化レベルは `-O2`（配信用）か `-O1`（検証用）に限定しています。
