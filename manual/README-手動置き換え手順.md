# Workflow ファイルの手動置き換え手順

自動 push ではワークフローファイル（`.github/workflows/` 以下）を変更する
権限がないため、ワークフロー変更があった場合はこの
`manual/build-and-release.yml` を **あなたの手で**
リポジトリの `.github/workflows/build-and-release.yml` に上書きしてください。

## 【最優先】前回の実行が失敗しました。もう一度の置き換えが必要です

まず、うまくいかなかったことをお詫びします。
適用していただいた版で実行された **run 33888888789 は失敗しました**
（4 時間 5 分で強制打ち切り）。原因は 2 つとも判明しており、
どちらも修正済みです。

### 原因 1：制限時間が足りていませんでした（私の設定ミス）

リンクの工程に **4 時間 00 分の上限**を設定していましたが、
実際の所要は **4 時間 02 分**でした。2 分足りません。
実行の最後のログに、まだ作業中だった証拠が残っていました。

```
Terminate orphan process: pid (6809) (wasm-opt)
```

計測して「4 時間 02 分かかる」と分かっていたのに、
上限を 4 時間ちょうどに設定していたのは明確に私の誤りです。
**5 時間 30 分に引き上げました。**

### 原因 2：同じファイルを 406 個も作り直していました

こちらのほうが重要です。
分割ビルドは「コンパイル済みの部品を集めてリンクするだけ」のはずですが、
実際にはリンクの担当ジョブが **440 個中 406 個を作り直していました**。
これだけで **約 19 分**を捨てていました。

理由を平たく言うと、こうです。

- 部品を作るとき、コンパイラは「この部品はどのファイルを参照したか」の
  メモ（`.d` ファイル）を一緒に残します
- そのメモには **ファイルの住所（絶対パス）** が書かれています
- ところが GitHub Actions は、ジョブごとに
  **毎回違うフォルダ名（ランダムな UUID）** でコンパイラを展開します
- するとリンク担当のジョブから見ると、メモに書かれた住所は
  **どこにも存在しない場所**になります
- `make` は「参照先が見つからない＝古くなったに違いない」と判断して、
  作り直しを始めてしまいます

実際に調べたところ、9 個のジョブすべてでフォルダ名が違っていました。

| ジョブ | コンパイラの展開先 |
|---|---|
| コンパイル shard-0 | `_temp/e7b82ce1-.../emsdk-main` |
| コンパイル shard-1 | `_temp/17ed1ac2-.../emsdk-main` |
| （中略。shard-2〜7 もすべて別） | |
| **リンク** | `_temp/927d2ddc-.../emsdk-main` |

**対策：リンクの工程では、このメモを捨てることにしました。**
メモは「ソースを書き換えたとき、どの部品を作り直すか」を知るためのもので、
リンクするだけの場面では最初から必要ありません。
捨てても出来上がるものは変わりません。

手元の再現テストで、作り直しが **完全にゼロ**になることを確認しました。

### つまり、次はこうなります

| | 前回（失敗） | 今回 |
|---|---|---|
| 無駄な作り直し | 406 個 / 19 分 | **0 個** |
| リンクの上限 | 4 時間 00 分（足りない） | **5 時間 30 分** |
| 最適化レベル | `-Os`（4 時間 02 分） | **`-O2`** |
| `wasm-opt` の版 | 116（emsdk 同梱） | **132（差し替え）** |
| リンク所要の見込み | 4 時間 02 分 | **約 2 時間 28 分** |
| 結果 | 打ち切り | 完走する見込み |

### なぜ `wasm-opt` の差し替えでそんなに縮むのか

ビルド 4 時間の **93%** は `wasm-opt` という 1 つのプログラムです。
さらにその中身を測ると、**71%** が「インライン展開」という
処理に使われていました。

調べたところ、この処理は **私たちが使っている版（116）の直後に、
本家が高速化していました**（2024年9月の PR #6966 / #6967。
本家の説明では「2 倍以上速くなる」「実際の大きなファイルで 5 倍」）。
私たちの版は、その修正が入る 9 か月前のものでした。

そこで `wasm-opt` だけを最新の版 132 に差し替えて実測したところ、
**37.8% 速くなり、出来上がるファイルの大きさはほぼ変わりません**
（+0.14%）。しかも規模が大きいほど効きが良くなるので、
本番ではもっと縮む可能性があります。

**ダウンロードに失敗しても、ビルドは止まりません。**
その場合は元の版 116 のまま続行します（遅くなるだけで、
出来上がるものは正しいままです）。

**なお `-Os` は使えなくなりました。** 版 132 と `-Os` の組み合わせは
**ビルドは成功するのに、ブラウザで開くと起動しない**という
厄介な壊れ方をします。そのため設定の入口で拒否するようにしてあります。

## 【PR #6 の回】置き換えが【必須】です（構成が大きく変わります）

今回の更新は **ワークフローの構成そのものを作り替えています**。
置き換えないと、ビルド時間の短縮も進捗バーも一切効きません。

### 何が変わったか

これまでは **1 つのジョブ**が「440 ファイルのコンパイル → リンク →
データ同梱」を順番にやっていました（所要 約 4 時間）。
今回それを **6 つのジョブに分けて、できるところを同時に走らせます**。

```
    計画 ──┬──> コンパイル（8並列） ──> リンク ──┐
           │                                      ├──> 組み立て ──> 公開
           └──> データ同梱 ───────────────────────┘
```

速くなる理由は 3 つです。

1. **コンパイルを 8 個のジョブに分割**
   GitHub Actions はジョブを別々のマシンで同時に動かせます。
   1 台 4 コアなので、8 分割すれば実質 32 並列相当になります。
   1 ジョブあたり 55 ファイルの担当です。
2. **データ同梱を同時進行に**
   ゲームデータ（`data/` と `gfx/`）の圧縮は、プログラム本体
   （`.wasm`）と無関係に進められます。これまではリンクが終わるのを
   待ってから始めていたので、その待ち時間が丸ごと無駄でした。
3. **コンパイル結果の再利用（ccache）**
   前回のビルドと変わっていないファイルは、コンパイルを丸ごと
   飛ばします。手元の計測では 7 秒 → 0 秒になりました。
   2 回目以降のビルドが大幅に速くなります。

### 【訂正】リンクの工程も速くできました

以前ここには「リンクの工程は速くできません。これが技術的な限界です」と
書いていましたが、**これは誤りでした。実測して撤回します。**

成功したビルド（4 時間 23 分）のログを 2218 回分集計したところ、
時間の使われ方はこうなっていました。

| 何が | どれだけ | 割合 |
|---|---|---|
| **`wasm-opt`（リンクの最適化）** | **4 時間 02 分** | **93%** |
| コンパイル（440 ファイル） | 約 15 分 | 6% |
| その他 | 数分 | 1% |

つまり「ビルドが 4 時間」は、ほぼ **`wasm-opt` 1 個が 4 時間**という話でした。

さらに調べると:

- `wasm-opt` は **4 コアのうち 1.05 コアしか使っていません**。
  マシンを強くしても速くなりません
- メモリも 16GB のうち 6.5GB しか使っていません。余っています
- 遅い原因は（これまで書いていた）Asyncify ではなく、
  **インライン展開という処理が 71%** を占めていました

インライン展開は最適化レベルで調整できるので、
レベルを下げれば実際に短くなります。本番と同じ条件で測った結果:

| 最適化レベル | リンクの時間 | 出来上がるサイズ |
|---|---|---|
| `-Os`（従来） | 4 時間 02 分 | 基準 |
| **`-O2`** | **約 3 時間 14 分（-20%）** | +2.7% |
| **`-O1`** | **約 53 分（-78%）** | +2.6% |

`-O1` にしてもサイズはたった 2.6% しか増えません
（以前「18 倍に膨れる」と書いていましたが、これも小さなテスト用
プログラムで測った誤りでした）。4GB メモリの機械でも問題なく動きます。

**そこで、実行時に選べるようにしました。**

- **`O2`（既定・配信用）**… 約 3 時間 14 分。公開する版を作るとき
- **`O1`（検証用）**… **約 53 分**。直した内容を試すとき

「直して → 焼いて → 遊んで確かめる」を繰り返すときは `O1` を選んでください。
4 時間だと 1 日 1 回しか試せませんが、53 分なら 1 日に何回も試せます。

### さらに：同じものは作り直しません（リンク結果のキャッシュ）

`wasm-opt` は「同じ材料を入れたら同じものが出てくる」処理です。
ですので、前回と材料が完全に一致していれば
**4 時間ぶんの処理をまるごと飛ばせます**。

実際の改良作業では、次のような「プログラム本体を 1 文字も
触っていない」変更がよく起きます。

- ゲームデータ（`data/` や `gfx/`）だけ直した
- MOD を足した
- 画面の HTML だけ直した
- ビルドの設定だけ直した

こういうときは、これまで **何も変えていないのに 4 時間待つ**
状態でした。今回からは **約 15 分で終わります**。

| 何を直したか | 従来 | これから |
|---|---|---|
| プログラム本体（配信用 `O2`） | 4 時間 23 分 | 約 3 時間 30 分 |
| プログラム本体（検証用 `O1`） | 4 時間 23 分 | **約 1 時間 10 分** |
| **データ・MOD・HTML・設定だけ** | 4 時間 23 分 | **約 15 分** |
| 同じ内容でもう一度実行 | 4 時間 23 分 | **約 15 分** |

判定は中身のハッシュ（指紋）で行います。
「ファイルの日付が変わっただけ」では作り直しませんし、
逆に**少しでも中身が違えば必ず作り直します**。
「直したのに古いものが公開される」ことは起きません。

短縮されるのはコンパイル段とデータ同梱に加えて、
**リンク段そのもの**です。

### 進捗バーについて

各ジョブが、こういう表示を出し続けます。

```
[PROGRESS] compile shard-2 [############------------------]  40% ( 22/ 55) 経過 3m12s 残り推定 4m48s
```

さらに実行結果のページ（Summary）に、どの工程が何分かかったかの
表が出ます。次回どこを改善すべきかが一目で分かります。

なお、リンクは内部の進み具合を数で数えられないため、
代わりに **「いま何の処理をしているか」を工程名で出します**。

```
[PROGRESS] リンク  工程: wasm-opt（最適化）  経過 42m10s / 想定 194m
```

`wasm-opt` がリンク時間の 93% を占めるので、この表示が出ている間は
「重い処理中」だと分かります。想定所要時間も、選んだ最適化レベルに
応じて実測値から出すようにしました（従来は 45 分固定で、
実際の 4 時間 02 分と 5 倍以上ずれていました）。

### 追加された入力項目

ビルド実行時に 2 つの項目を選べるようになりました。

**1. コンパイルの分割数**（4 / 6 / 8 / 12、既定 8）

- 分割を増やすとコンパイルは速くなりますが、
  中間ファイル（合計 1GB 超）の転送が増えます
- 増やしすぎると転送の待ち時間が勝って**逆に遅くなります**
- まずは既定の 8 でお試しください

**2. リンク最適化レベル**（`O2` / `O1`、既定 `O2`）← 今回追加

| 選択 | 全体の所要 | いつ使うか |
|---|---|---|
| `O2` | 約 3 時間 30 分 | **公開する版を作るとき** |
| `O1` | **約 1 時間 10 分** | **直した内容を試すとき** |

出来上がるファイルのサイズ差は 2.6% しかないので、
`O1` で作ったものでも普通に遊べます。
遊んで確かめて、良ければ最後に `O2` で焼き直す、という使い方を想定しています。

## （前回 PR #5 の回）置き換えが【必須】でした

今回の更新（読み込み高速化・日本語入力バグ修正・マップ移動の軽量化）には
ワークフロー本体の変更が含まれています。**マージ後に必ず下記の
「置き換え手順」を実行してください**。置き換えないと:

- 新パッチ `cdda-0I-emscripten-json-cache.patch`（JSON 解析キャッシュの
  永続化 = 2 回目以降のロード短縮）が**ビルドに取り込まれず**、
  検証 grep も走りません
- コンパイル最適化の `-Os` → **`-O3`** 変更（マップ移動の軽量化の柱）が
  反映されません

今回ワークフローに入った変更は次の 3 点です:

1. **JSON キャッシュ永続化パッチの適用ステップ追加**
   （`git apply ../patches/cdda-0I-emscripten-json-cache.patch`）
2. **コンパイル最適化を `-O3` に変更**（emscripten ブランチの
   `OPTLEVEL = -Os` だけを書き換える限定 sed + 確認用 awk）。
   ビルド時間は多少伸びる可能性がありますが、リンク段の `-Os` は
   維持しているため wasm サイズの増加は限定的です
3. **新パッチの検証 grep を 5 行追加**（IME ゲーティング / 描画 yield
   間引き / input_context スタック / JSON キャッシュ / immutable root）

## （前回 PR #3 の回）置き換えが【必須】でした

今回の更新には、ワークフロー本体の設定変更が含まれています。
置き換えないと以下の改善が反映されません:

1. **SIGILL クラッシュ対策**（ワールド作成直後・キャラ作成直後のロード中に
   まれに発生していたもの）:
   - Asyncify 退避バッファを 4MiB → **16MiB** に拡大
     （深い呼び出し中の巻き戻しでバッファが尽きると SIGILL 型のトラップに
     なるため、観測された最深チェーンより十分上に上限を設定）
   - wasm メインスタックを 1MiB → **4MiB** に拡大
     （マップ生成の再帰でのスタック枯渇も SIGILL 型トラップの原因）
2. **動作の高速化**: リンク最適化を `-O0` → 本家標準の **`-Os`** に変更。
   これまで `-O0` でビルド時間を短縮していましたが、Asyncify 計装が
   未最適化のまま残るため、プレイ中の動作が全体的に重くなっていました。
   `-Os` は本家が Web 版の公式ビルドに使っている実績ある設定です。
   （代わりにビルド時間は 1〜2 時間 → 2〜3 時間程度に伸びます）
3. **Stats Through Kills MOD の同梱**: リポジトリの `mods/` フォルダを
   ゲームデータに同梱するステップを追加。初回はキル経験値 MOD
   「Stats Through Kills」が入ります（ワールド作成時の MOD 一覧に表示）。
4. **日本語入力（IME）対応の検証行**: パッチが正しく当たったかを CI が
   確認する grep を 2 行追加。

## 置き換え手順（ブラウザだけで完結、5分）

1. ブラウザで以下を開く:
   https://github.com/LBTStudio/CDDA-broser/blob/main/manual/build-and-release.yml
   （プルリクエストをマージした**あと**に開いてください）
2. 右上の「Raw」ボタンを押し、表示された全文を Ctrl+A → Ctrl+C でコピー
3. 次に以下を開く:
   https://github.com/LBTStudio/CDDA-broser/blob/main/.github/workflows/build-and-release.yml
4. 右上の鉛筆アイコン（Edit this file）を押す
5. エディタ内を Ctrl+A で全選択 → Ctrl+V で貼り付け（全文置き換え）
6. 右上の緑ボタン「Commit changes...」を押す
7. 出てきたダイアログで:
   - Commit message はそのままで OK
   - 「Commit directly to the `main` branch」が選ばれていることを確認
   - 緑の「Commit changes」を押す

これで完了です。そのあと Actions からビルドを実行してください
（手順は PR の説明文にあります）。
